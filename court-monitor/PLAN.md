# Мониторинг судебных дел из Битрикс24

Новый проект. Задача та же — брать данные с сайтов судов ГАС «Правосудие», но **без ИИ-агента и без диалога**.

Нужен инструмент, который **раз в сутки** по сделкам в Битрикс24 (номер дела) ходит на сайт суда, актуализирует карточку и **если что-то изменилось — пишет клиенту статус**.

Старый контур «Анна / Ноя / MCP / живой чат» **не используем**. Из прошлого проекта берём только проверенный парсер карточки дела (`court-kb/scraper/case_lookup/`) и опыт с RU-прокси.

---

## 1. Что система делает

```text
Битрикс24 (сделки с номером дела)
        │  ежедневно, пачками
        ▼
Планировщик (cron / systemd)
        │
        ▼
Сервис мониторинга
   1. Выбрать активные сделки
   2. Для каждой: сайт суда → карточка дела
   3. Сравнить со снимком вчера
   4. Записать новое состояние в Битрикс
   5. Если diff ≠ ∅ → сообщение клиенту
   6. Журнал прогона (успех / капча / блок / нет дела)
```

ИИ не участвует: ни генерация текста, ни «ответ на вопрос». Текст клиенту — **шаблон** из полей карточки.

---

## 2. Границы MVP

**Входит**

- Источник дел: сделки CRM Битрикс24 с заполненным номером дела.
- Источник статуса: официальный сайт суда (сначала ГАС «Правосудие», `sud_delo`).
- Сравнение снимков и уведомление только при изменении.
- Запись актуального статуса обратно в поля сделки.
- Один канал исходящих: то, что уже есть у клиента в Битрикс (открытая линия / SMS / почта) — выбирается на шаге 0.

**Не входит в MVP**

- Чат с ботом, Ноя, MCP, «спроси что угодно про суд».
- Поиск по ФИО без номера дела.
- `kad.arbitr.ru`, SudAct, mos-gorsud.
- Юридические советы и прогнозы исхода.
- Обход WAF/капчи как «взлом»: только легальный доступ (резидентный RU-прокси, паузы, уважение `robots` где применимо).

**Пилот:** 6 райсудов Воронежа (уже отлаженный HTML). Дальше — любой суд из справочника, если в сделке есть URL или код суда.

---

## 3. Данные, которые надо согласовать в Битрикс (шаг 0, до кода)

Без этого поля гадать нельзя. Нужна 30-минутная сверка с карточкой сделки.

| Смысл | Где в Битрикс | Обязательно |
| --- | --- | --- |
| Номер дела (`2-1248/2026`) | пользовательское поле сделки, например `UF_CRM_CASE_NUMBER` | да |
| Суд (название / slug / URL сайта) | поле или справочник | да, иначе некуда ходить |
| Стадия / воронка «ведём дело» | `STAGE_ID` / категория | да, чтобы не мониторить закрытые |
| Контакт клиента (телефон, chat id, email) | контакт сделки | да |
| Снимок статуса (JSON или текст) | служебное UF-поле | да, чтобы считать diff |
| Дата последней проверки / ошибка парсера | служебные UF | желательно |
| Согласие на рассылку статуса | галочка / стадия | да, 152-ФЗ |

Если суда в сделке нет — на пилоте маппим номер дела → воронежский суд вручную или отдельным полем.

## 4. Целевая архитектура

```
┌─────────────┐     REST webhook      ┌──────────────────┐
│  Битрикс24  │◄──────────────────────►│  court-monitor   │
│  сделки     │  list / get / update  │  (Python, РФ VPS)│
└──────▲──────┘                       │                  │
       │ imessage / SMS / OL          │  ┌────────────┐  │
       └──────────────────────────────│──│ notifier   │  │
                                      │  └────────────┘  │
                                      │  ┌────────────┐  │
                                      │  │ parser     │──┼──► sudrf.ru (через RU residential proxy)
                                      │  └────────────┘  │
                                      │  ┌────────────┐  │
                                      │  │ snapshots  │  │  SQLite/Postgres
                                      │  └────────────┘  │
                                      └────────┬─────────┘
                                               │ cron 06:00 MSK
                                               ▼
                                         systemd timer
```

**Почему не Ноя и не n8n как мозг:** оркестрация простая (раз в день, цикл по сделкам). n8n можно оставить только как таймер, если уже стоит; логика сравнения и парсинга — в сервисе.

**Где крутить:** VPS в РФ + **резидентный/мобильный** прокси. Датацентровые IP (в т.ч. российский shared-хостинг) ГАС часто режет: HTML-заглушка «заблокирован (G)» или TCP timeout. Это уже проверено на прошлом проекте.

## 5. Пошаговый план реализации

### Шаг 0. Уточнения у заказчика (1 встреча)

1. Портал Битрикс (облако / коробка), есть ли входящий вебхук с правами CRM.
2. Имена UF-полей: номер дела, суд, телефон.
3. Канал сообщения клиенту: WhatsApp/Telegram через ОЛ, SMS, email, комментарий только менеджеру.
4. Текст шаблона и что считать «изменением» (любая строка движения / только статус и дата заседания).
5. Час запуска и лимит дел в сутки (прокси и капча не бесконечны).
6. Кому слать ошибки (чат юристов), а не клиенту.

Пока ответы не зафиксированы — в коде закладываем конфиг, не хардкод.

### Шаг 1. Каркас репозитория

Новая папка `court-monitor/` (этот документ — входная точка).

```
court-monitor/
  PLAN.md
  README.md
  pyproject.toml / requirements.txt
  src/court_monitor/
    bitrix.py          # crm.deal.list / get / update, контакты
    parser/            # адаптер над старым case_lookup
    snapshot.py        # hash + JSON карточки
    diff.py            # сравнение полей
    notify.py          # шаблон + отправка через Битрикс
    job.py             # один дневной прогон
    models.py
  tests/
  deploy/              # systemd timer, .env.example
```

Парсер **копируем/подключаем** из ветки `cursor/court-sites-kb-scraper-5631` (`scraper/case_lookup`, `fetch`, `proxy_pool`), выкидываем MCP, промпт Анны, БЗ Нои.

### Шаг 2. Адаптер Битрикс24

- Входящий вебхук: `https://<portal>/rest/<user>/<code>/`.
- `crm.deal.list`: фильтр по стадии + непустое поле номера дела; `select`: `ID`, `TITLE`, `CONTACT_ID`, `STAGE_ID`, `UF_*`.
- Пагинация `start` (50 записей).
- `crm.deal.contact.items` / `crm.contact.get` + `crm.duplicate` не нужны, если телефон в контакте: `crm.contact.get` → `PHONE`, `IM`.
- `crm.deal.update`: записать статус, дату заседания, JSON-снимок, `LAST_CHECK_AT`, при ошибке — `PARSE_ERROR` (клиенту не слать).
- Ограничение REST: пауза, не долбить портал в цикле без backoff.

Тест: скрипт `list-deals` печатает id + номер дела, ничего не пишет.

### Шаг 3. Нормализация номера и выбор суда

- Нормализатор из прошлого проекта: обрезать `~ М-52/2026`, пробелы, латинские «C».
- Резолв суда: поле URL → origin; иначе slug из справочника `courts.yaml`; на пилоте — 6 воронежских.
- Если суда нет — сделка в журнал ошибок, пропуск.

### Шаг 4. Парсер карточки (слой «сайт суда»)

Переиспользовать `search_case_direct` / разбор HTML:

- номер, UID, даты, судья, категория, результат, стороны, движение, URL карточки.
- Паузы между запросами, sticky «последний живой прокси», детект WAF-заглушки.
- Капча: сначала эвристика без решения; если форма с капчей — **очередь на ручной/2captcha только если заказчик явно ок**, иначе статус `needs_captcha` менеджеру, не клиенту.
- Таймаут на дело ~40 с; не параллелить десятки судов с одного IP.

Контракт внутренней функции:

```python
lookup(court_url, case_number) -> CaseCard | NotFound | Blocked | Captcha
```

Юнит-тесты на уже существующих HTML-фикстурах (`2-1248` Советский и т.д.).

### Шаг 5. Снимки и diff

Хранить **два слоя**:

1. В Битрикс — короткое человекочитаемое поле «Статус на сайте» + дата заседания (видит менеджер).
2. В БД сервиса — полный JSON + `content_hash`.

Считать изменением (настраиваемый список):

- результат / стадия дела;
- дата, время, зал заседания;
- новая строка в движении;
- смена судьи.

Не считать изменением:

- перестановку HTML, лишние пробелы, порядок атрибутов;
- смену URL с одинаковым UID.

Если карточка не найдена два дня подряд — алерт менеджеру, не клиенту.

### Шаг 6. Сообщение клиенту (шаблон, не LLM)

Пример:

```
По делу {case_number} ({court_name}) появились изменения.

Статус: {result_or_stage}
Следующее заседание: {hearing_dt} {hall}
Последнее движение: {last_move}

Карточка: {card_url}
```

Отправка (выбор на шаге 0):

1. **Открытые линии Битрикс** — `imopenlines.message.add` / сообщение в чат с клиентом, если диалог уже есть.
2. **SMS** — `messageservice.message.add` при подключённом провайдере.
3. **Почта** — `crm.activity.add` типа email.
4. Запасной вариант MVP: **уведомление ответственному** (`im.notify`) + задача «написать клиенту», если исходящий канал ещё не согласован.

Правила:

- не слать полный перечень сторон и лишние ПДн;
- не слать при `Blocked` / `Captcha` / `NotFound`;
- антидубль: один diff-hash на сделку в сутки.

### Шаг 7. Дневной job

Порядок одного прогона (`job.py`):

1. Взять lock-файл (не запустить второй cron).
2. Выгрузить сделки.
3. Для каждой: lookup → diff → update Bitrix → notify при необходимости.
4. Sleep 3–8 с между судами / прокси.
5. Сводка в лог и в чат юристам: `проверено N, изменений M, ошибок E`.

Расписание: systemd timer `OnCalendar=*-*-* 06:00:00` Europe/Moscow (до начала рабочего дня).

Опционально позже: вебхук `onCrmDealAdd` — первая проверка сразу, не ждать утра.

### Шаг 8. Наблюдаемость и безопасность

- Логи без полного ФИО третьих лиц (или хэш).
- Секреты только в `.env` на VPS: вебхук Битрикс, прокси, ключ 2captcha.
- Метрики: success rate, доля captcha/WAF, время lookup.
- 152-ФЗ: передаём клиенту только то, что и так публично на сайте суда по **его** делу, и только при согласии в сделке.

### Шаг 9. Пилот

1. 5–10 реальных сделок Воронежа с известными номерами (в т.ч. уже проверенные `2-1248/2026`, `2-3588/2026`).
2. Сухой прогон: `DRY_RUN=1` — парсим и пишем diff в лог, **не** трогаем клиента.
3. Прогон с записью в Битрикс, без notify.
4. Notify только на тестовый контакт.
5. Включение боя.

Критерий готовности пилота: 3 дня подряд прогон без ручного рестарта, изменения на сайте → сообщение у тестового клиента, ложные срабатывания < 1/день.

### Шаг 10. Расширение после пилота

- Справочник судов РФ (уже есть `directory/courts-ru.json` в старом репо) → URL по названию суда из сделки.
- Мировые судьи (другие шаблоны сайтов).
- Арбитраж отдельным адаптером, не смешивать с sudrf.
- Ручной «Проверить сейчас» в смарт-процессе / кнопке Битрикс (исходящий вебхук).

## 6. Порядок работ в коде (спринты)

| Спринт | Результат | Зависимости |
| --- | --- | --- |
| A | Каркас, конфиг, тесты нормализации номера | нет |
| B | `bitrix.py`: list/update на песочнице/вебхуке | шаг 0, вебхук |
| C | Врезка парсера + прокси, lookup по фикстурам и 1 живому суду | RU-прокси |
| D | Снимки, diff, DRY_RUN по списку сделок | B+C |
| E | Шаблон + канал notify | канал в Битрикс |
| F | systemd timer, алерты, пилот | D+E |

## 7. Риски (уже известны)

| Риск | Что делаем |
| --- | --- |
| WAF / DC IP | только residential RU proxy, sticky, ротация |
| Капча на `sud_delo` | не спамить; очередь менеджеру; опционально 2captcha по договору |
| Разные поля формы у судов | discover формы, пилот на 6 одинаковых шаблонах |
| Нет официального API ГАС | только HTML, хрупко — фикстуры + мониторинг парсера |
| ПДн в карточке | шаблон без лишнего; согласие в сделке |
| Лимиты REST Битрикс | пагинация, backoff |
