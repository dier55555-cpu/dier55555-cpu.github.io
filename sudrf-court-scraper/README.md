# Парсер сайтов судов (sudrf.ru) → база знаний для ИИ-агента

Инструмент собирает информацию с сайтов районных судов на платформе
ГАС «Правосудие» (sudrf.ru) и превращает её в базу знаний (БЗ), которую
можно либо загрузить статическим файлом в агента (например, в НОЕ),
либо отдавать «живым» MCP-инструментом.

Сайты из задачи (все — районные суды г. Воронежа, `courts.json`):

- https://sovetsky--vrn.sudrf.ru/
- https://kominternovsky--vrn.sudrf.ru/
- https://zheleznodorozhny--vrn.sudrf.ru/
- https://levoberezhny--vrn.sudrf.ru/
- https://centralny--vrn.sudrf.ru/
- https://lensud--vrn.sudrf.ru/

## ⚠️ Важное открытие: сайты блокируют доступ из-за рубежа

Проверил доступ к этим сайтам напрямую из облачной среды агента: TLS-соединение
обрывается на этапе Client Hello (`Connection reset by peer`), при этом сервер
отдаёт заголовок `Server: BigIP`. HTTP (порт 80) отвечает `302 → https`, то есть
хост жив, но фильтрация происходит на уровне F5 BigIP WAF **до** отработки HTTPS —
это типичное поведение sudrf.ru при обращении с зарубежных/датацентровых IP
(гособъекты ГАС «Правосудие» массово блокируют иностранные подсети).

**Следствие:** сборщик данных нужно запускать с хоста с российским IP —
обычный VPS в РФ, либо HTTP(S)-прокси с российским выходным IP. Никакой код
это не обходит «магией» — это сетевой уровень, а не вопрос заголовков/user-agent.
В скрипте это учтено: сессия поддерживает прокси через `--proxy` или переменную
окружения `SUDRF_PROXY`.

Из-за этого ограничения весь пайплайн ниже проверен на локальных HTML-фикстурах,
имитирующих типовую вёрстку ГАС «Правосудие» (см. `tests/fixtures/`), а не на
реальных сайтах — запустить финальный сбор с реальных URL нужно будет с
российского сервера/прокси.

## Архитектура решения

```
courts.json ──▶ crawler.py (обход сайта суда) ──▶ parse.py (текст, разделы, контакты)
                                                        │
                                                        ▼
                                    data/<slug>.json  (сырой дамп страниц)
                                                        │
                                    ┌───────────────────┴───────────────────┐
                                    ▼                                       ▼
                    output/<slug>/*.md, _all.md               search.py (in-memory поиск)
                    output/index.json                                      │
                    (для статичной загрузки в БЗ агента)      mcp_server.py (MCP-инструменты
                                                                  list_courts / get_court_info /
                                                                  search_court_info — для «живого»
                                                                  доступа агента к данным)
```

Два способа отдать данные агенту в НОЕ — выбирайте по тому, что поддерживает
платформа:

1. **Статическая база знаний (проще всего).** Запустить сборщик, загрузить
   получившиеся `output/<slug>/_all.md` (по одному файлу на суд, или все сразу)
   в раздел «База знаний» агента в НОЕ. Обновлять по расписанию (см. ниже) и
   перезаливать файлы. Плюсы: не нужен отдельный сервер, работает с любой
   платформой, поддерживающей загрузку файлов в БЗ/RAG. Минусы: данные не
   real-time, обновление — раз в N часов/суток по cron.

2. **Живой MCP-инструмент.** Поднять `mcp_server.py` на сервере с
   российским IP (там же, где крутится сборщик) и подключить его к агенту в
   НОЕ как MCP-коннектор по HTTP (`--transport streamable-http`). Агент сам
   вызывает `search_court_info("график приёма", court_slug="sovetsky-vrn")`
   и получает свежие данные без ручной перезагрузки БЗ. Плюсы: агент может
   уточнять/сужать запрос, всегда видит последний скрап (`reload_knowledge_base`
   вызывается после каждого прогона cron). Минусы: нужен отдельный
   постоянно работающий процесс и доступность его извне для НОЕ.

Рекомендация: начать с варианта 1 (быстрее подключить), при необходимости
добавить вариант 2 — код для обоих уже готов и использует общие данные.

## Установка

```bash
cd sudrf-court-scraper
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

## Сбор данных

```bash
# С сервера/прокси с российским IP:
python -m sudrf_scraper.cli --proxy http://user:pass@ru-proxy-host:port -v

# Или указать прокси через переменную окружения:
export SUDRF_PROXY=http://user:pass@ru-proxy-host:port
python -m sudrf_scraper.cli -v

# Только конкретные суды:
python -m sudrf_scraper.cli --only sovetsky-vrn centralny-vrn -v
```

Результат:

- `data/<slug>.json` — сырой дамп всех страниц суда (для дебага/повторной обработки);
- `output/<slug>/_all.md` — единый markdown-файл на суд (загружать в БЗ);
- `output/<slug>/<раздел>.md` — то же самое отдельными файлами по разделам;
- `output/index.json` — сводка по всем судам (контакты, разделы, дата сбора).

По умолчанию обходятся страницы одного домена в глубину до 3 переходов
(до 60 страниц на сайт), с распознаванием типовых разделов ГАС «Правосудие»:
`about`, `contacts`, `requisites`, `reception`, `judges`, `structure`,
`jurisdiction`, `filing`, `news`, `schedule`. Телефоны и email вытаскиваются
автоматически регулярками по всему собранному тексту.

## Автообновление (cron)

Данные на сайтах судов меняются (новости, график приёма, иногда контакты),
поэтому сборщик стоит гонять по расписанию, например раз в сутки ночью:

```cron
0 3 * * * cd /path/to/sudrf-court-scraper && \
  SUDRF_PROXY=http://user:pass@ru-proxy-host:port \
  .venv/bin/python -m sudrf_scraper.cli -v >> /var/log/sudrf-scraper.log 2>&1
```

Если используете вариант с MCP-сервером — он сам подхватит новые данные
из `data/` при следующем вызове `reload_knowledge_base`, либо перезапускайте
процесс после каждого прогона cron.

## MCP-сервер (живой доступ агента к данным)

```bash
# Локально по stdio (для отладки/локальных клиентов):
python -m sudrf_scraper.mcp_server

# По HTTP — чтобы платформа НОЕ подключилась по URL как к MCP-коннектору:
python -m sudrf_scraper.mcp_server --transport streamable-http --host 0.0.0.0 --port 8765
```

Инструменты, которые увидит агент:

- `list_courts()` — список судов с контактами и датой последнего обновления;
- `get_court_info(court_slug)` — контакты и разделы по одному суду;
- `search_court_info(query, court_slug=None, limit=5)` — поиск по текстам
  всех собранных страниц (реквизиты, график приёма, порядок подачи документов
  и т.п.), с указанием источника (URL);
- `reload_knowledge_base()` — перечитать `data/*.json` без перезапуска процесса.

В проде процесс нужно держать за reverse-proxy с HTTPS и ограничением доступа
(например, basic-auth/allowlist по IP НОЕ), т.к. `mcp.server.fastmcp` сам по
себе не добавляет авторизацию.

## Тесты

Реальные сайты недоступны из большинства сред разработки (см. блокировку
выше), поэтому тесты гоняют весь пайплайн (`fetch → parse → crawl → kb_builder
→ search`) на локальном HTTP-сервере с фикстурами, имитирующими типовую
вёрстку ГАС «Правосудие»:

```bash
pip install pytest
python -m pytest tests/ -v
```

## Что уточнить перед боевым запуском

1. **Прокси/сервер с российским IP** — без него сбор данных не заработает
   (см. раздел про блокировку).
2. **Какие именно разделы важны агенту** — сейчас тянутся все текстовые
   страницы домена; если агенту нужны только контакты/реквизиты/график приёма,
   можно сузить обход (`--max-depth 1`) и не индексировать новости/большие
   архивные разделы.
3. **Точные названия судов** в `courts.json` — заполнены по шаблону URL,
   при первом реальном прогоне сборщик сам подтянет точный `<title>`/`<h1>`
   с сайта (можно поправить `name` в `courts.json` по факту).
4. **Способ доставки в НОЕ** — если платформа поддерживает MCP-коннекторы
   по URL, лучше вариант 2 (живой поиск); если только загрузка файлов в БЗ —
   вариант 1 и cron с перезаливкой `output/*/_all.md`.
