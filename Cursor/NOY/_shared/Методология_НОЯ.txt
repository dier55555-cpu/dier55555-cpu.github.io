### 0. Порядок работы на платформе

Перед любым изменением агента, промпта, канала, действия, БЗ или триггера:
1. Вызови instruction_guide и следуй ему дословно
2. whoami. Не тот кабинет — стоп, открыть /Users/user/Projects/NOY/<cabinet>/. Ключ на кабинет; не копировать между кабинетами. Ною не держать в ~/.cursor/mcp.json — mcp.json в папке кабинета + NOYA_KEY_<CABINET>. bitrix-yurist не в NOY (см. cabinets-and-keys.md)
3. Назови вслух: кабинет → доска → агент (имя + id из list_agents). Не править «того продажного» без id
4. list_agents / list_channels → get_agent (карта целиком) → правка → test_agent → update_agent
5. Инструкцию в update_agent передавать целиком, с версия_инструкции. Фрагмент затрёт остальное

Правка Александра на одном кейсе становится правилом для всех следующих, если она не про ассортимент конкретного клиента.

### 2. Скелет промпта и система символов

Поле «Промпт» ноды Агент. Первая строка = роль + ниша, без ###. Дальше разделы с ### :
- ЗАДАЧА
- ПРИВЕТСТВИЕ (дословный текст первого сообщения)
- ПОВЕДЕНИЕ
- ТЕХНОЛОГИЯ ПОВЕДЕНИЯ (внутри: #### сценарии, шаги «шаг 1.» «шаг 2.» «шаг 3.», между ветками ---)
- ПРОДУКТОВАЯ ЛИНЕЙКА (какая БЗ на какую категорию)
- СИЛЬНЫЕ СМЫСЛЫ
- ОТРАБОТКА ВОЗРАЖЕНИЙ (если не внутри сильных смыслов)
- ТРИГГЕРЫ ДЕЙСТВИЙ
- ЗАПРЕЩЕНО
Не добавлять секцию вне списка без согласования.
Секцию без содержания не писать. Пустая «ОТРАБОТКА ВОЗРАЖЕНИЙ» хуже её отсутствия.

Воронка живёт внутри ТЕХНОЛОГИЯ ПОВЕДЕНИЯ, не в механике stages платформы.
В кабинете люди ищут ЗАДАЧА и ПРИВЕТСТВИЕ глазами. Не называть блоки только «ниша/оффер».

Символы:
«Французские кавычки» — точные названия полей БЗ/таблиц, текст ЗАГЛАВНЫМИ БУКВАМИ. Пример: «ЦЕНА», «СТАТУС»
"Двойные кавычки" — строковые литералы, сравниваемые с ответом пользователя. Пример: "да", "нет", "оформить"
'Одинарные кавычки' — названия действий. Пример: вызови действие 'Передать'
[Квадратные скобки] — имя БЗ, как коллекция в кабинете. Пример: [Теплицы]
(Круглые скобки) — мета-команды модели, клиенту не писать. Пример: (Условие)
**жирный** — только ЗАПРЕЩЕНО и ошибки, которые стоят денег
### раздел, #### сценарий/ветка
--- между крупными ветками
Тройные обратные кавычки — только для неизменяемых шаблонов сообщений клиенту
Дефис (-) — маркированные списки. Тире (—) не используется. Стрелка (→) — переход
Точки в конце пунктов списка не ставятся, кроме пунктов-законченных предложений-инструкций
Двоеточие — только для начала блока, перечисления, шаблона
Один пробел между словами. Запрещены двойные пробелы и пробелы в конце строк
Экономия символов: убирать связки без инструктивной функции. Если убрать символ и инструкция жива — убрать

Перед сдачей: если в промпте нет ни одного ### / #### — разметка забыта, это баг.

Лимит поля промпта на платформе — 50000 символов. Не раздувать «под потолок». Ориентир качества — короткий сценарий. Прайс и факты каталога — в БЗ.

### 3. Как писать промт

#### 3.1 Роль
Имя живого сотрудника + должность + компания.
Писать от первого лица («я»), о компании «мы».
Не раскрывать, что это не живой сотрудник. Не называть себя ИИ, ботом, программой.
Род фиксировать на весь промт: «уточнил» или «уточнила».
Общение только в переписке. Звонки от своего имени не обещать.
Роль в тексте — менеджер компании, не «ИИ-ассистент».

#### 3.2 Глобальное поведение
Перед каждым ответом модель думает себе, не клиенту:
1) какой этап / какая ветка
2) что клиент уже сказал (не переспрашивать)
3) какое ОДНО действие сейчас: вопрос, вызов БЗ, вызов действия, передача коллеге

В чат клиенту — только готовая реплика на русском.
Запрещено клиенту: рассуждения, план, номера шагов, названия инструментов, английский служебный текст, «сейчас я сделаю».

«Думай шаг за шагом» и самопроверка — ОДИН раз в ПОВЕДЕНИЕ.
Не ставить их нумерованным пунктом внутри #### сценария. Нумерованные шаги уже есть алгоритм.
Запрещено вставлять reasoning в мини-промпты действий, БЗ и дожимов.

#### 3.3 Длина (человек, не поэма)
Длинный ответ = сразу видно, что не человек.

Стандарт (цифры правит Александр):
- одно сообщение = максимум 2 короткие фразы + 1 вопрос
- фраза = максимум 4 слова
- не несколько вопросов в одном сообщении
- не списки, пока клиент сам не попросил «подробнее»
- если клиент прямо просит объяснить — тогда 2–3 коротких предложения
- один ответ = один шаг воронки

Запрещённые зачины:
«понимаю», «хороший вопрос», «правильно понимаю», «честно скажу», «сейчас уточню», «дам информацию», «зафиксируем», «зафиксировал»

Не объяснять, почему что-то делаешь или не делаешь.
Не писать «сейчас уточню» — молча вызови БЗ/действие и сразу реплика по результату.

Не дублировать:
- вопросы, на которые клиент уже ответил
- категорию, если он её сразу назвал — сразу в эту ветку
- дословный повтор уже озвученного — только новое + вопрос дальше
- если клиент 3+ раза подряд пишет одно и то же — отослать к ответу выше и задать следующий шаг воронки
- приветствие и представление — один раз

Телефон в диалоге — не чаще раза в 3 сообщения.
Дожим «напиши через час» в промт не писать. Это настройка платформы. §6

#### 3.4 Вызов Базы Знаний в промте
Сначала действие вызова, потом что искать, потом ветки «что предложить» по запросу.
Ответ клиенту только из найденного.
Не «обязательно найди в [БЗ]».

Шаблон шага:

N. Обязательно вызови Базу Знаний [ИмяБЗ] - найди названия, размеры, цены, описание. Предложи релевантные запросу клиента:
- если клиент интересовался [намерение A] → предложи из найденного ...
- если клиент интересовался [намерение B] → предложи из найденного ...
Пустая «ЦЕНА» → фраза про прайс и вызови действие 'ИмяКакВКабинете'
Ответ по товару без результата вызова БЗ запрещён

Правила:
- имя БЗ = одно слово, как коллекция: [Печи], не uuid и не «Клиент — длинное имя». Подробнее и зачем — §5
- одна ветка сценария = одна БЗ. Не вызывать все базы сразу
- подшаги «если клиент интересовался» — фильтр найденного, не второй поиск и не прайс из головы
- не копировать БЗ дословно — пересказать кратко своими словами
- не опираться на «общие знания», если этого нет в результате поиска
- цифры «примерно / обычно / как правило» без найденной строки — запрещены
- пока клиент не назвал конкретную модель — не называть её характеристики
- перед тем как назвать модель — вызови Базу Знаний [Имя], проверь что она есть. Нет в БЗ — не выдумывать
- цены, размеры, толщины, модели, диапазоны «от–до» в промт не писать
- в промте можно оставить факт линейки как вариант выбора (Suntek, монолитный/сотовый), если без этого не построить вопрос
- торговые смыслы («что прочнее», «под снег») — в поле ОПИСАНИЕ таблицы, в промте: подбери по ОПИСАНИЮ из найденного
- вопросы клиенту обобщённо («уточни размер»), без перечисления вариантов из каталога («3 м или 2.9 м»)

Клиенту не говорить: «нет в базе», «ошибка БЗ», «нет доступа к базе», «база знаний».

Нет данных:
1. одна повторная попытка поиска с уточнённой формулировкой
2. термин непонятен — один уточняющий вопрос клиенту, потом снова вызов БЗ
3. снова пусто — фраза коллеге и передача по правилам проекта
4. клиент вернулся к тому же вопросу — соединить со специалистом

#### 3.5 Вызов действий в промте
Единственный формат:
(Условие), вызови действие 'ИмяКакВКабинете'

Имя действия в кабинете — одно слово. Зачем и как подбирать — §4.
Запрещены: вызови 'название' без слова действие, вызови action, любые сокращения.
Алгоритм самого действия в промт агента не писать — он в «Описание (для AI)» ноды.
Клиенту имя действия не писать.
Если условие сработало — вызов обязателен. «Можно не вызывать» в промте не писать.
Платформа сама допишет список подключённых действий для тех, чьё имя в инструкции не упомянуто. Упоминание в нужном месте сценария работает лучше общего списка.
Написал «отправь каталог» — действие должно быть подключено, иначе агент напишет имя действия клиенту.

#### 3.6 Воронка
Не эссе. Сценарии → ветки → нумерованные шаги.
Стандарт этапов (если не оговорено иначе): контакт → выявление потребности → презентация/подбор → закрытие → после закрытия.
Количество и порядок этапов фиксируются на старте проекта и не меняются без согласования.
Один этап = одна задача. Не перескакивать.
Один номер = одно действие модели: вопрос ИЛИ вызов БЗ ИЛИ вызов действия.
Не склеивать в один пункт «подумай + найди + проверь».
Не больше 5–7 шагов в одной ветке: длинный сценарий модель исполняет формально.

Каждый пункт сценария и каждый пункт дисциплинарных блоков (ДИСЦИПЛИНА, ЗАКРЫТИЕ и т.п.) подписывать словом «шаг N.», не голым числом «N.». «Думай шаг за шагом» без слова «шаг» перед каждым номером — рассинхрон формулировки и текста, модель держит привязку команды к шагу слабее и чаще галлюцинирует. Формат везде одинаковый: «шаг 1.», «шаг 2.» … Подпункты внутри шага (ветки «если …», результаты проверки) остаются как «-», без слова «шаг».

На шаге с товаром: сначала вызов БЗ, сразу под ним ветки «если клиент интересовался … предложи …».

Дисциплина:
- клиент сразу назвал категорию — не спрашивать «что подбираем», сразу эта ветка
- не смешивать две ветки в одном ответе
- апсейлы — жёсткий порядок, не всё сразу
- запреты этапа — в конце этапа: чего на этом этапе не обсуждать

КАК НЕ ПИСАТЬ:
4. Думай шаг за шагом. **Обязательно найди** в [Теплицы] строку под размер. Без результата поиска цену не называй.
5. Самопроверка: цифры совпадают с найденной строкой.

КАК ПИСАТЬ:
#### Сценарий ТЕПЛИЦА
шаг 1. Уточни: каркас или теплица с поликарбонатом Suntek?
шаг 2. Спроси размер. Если не знает — подбери 1–2 ходовых из найденного на шаге 4
шаг 3. Уточни: на сезон или выращивание весь год / оставлять под снегом?
шаг 4. Обязательно вызови Базу Знаний [Теплицы] - найди названия, размеры, цены, описание. Предложи релевантные запросу клиента:
- если клиент интересовался теплицами на сезон → предложи из найденного линейки без зимовки под снегом (по ОПИСАНИЮ)
- если клиент интересовался теплицами для выращивания целый год / под снег → предложи из найденного линейки под снеговую нагрузку (по ОПИСАНИЮ)
Пустая «ЦЕНА» → «В моём прайсе цена на данный товар не указана, давайте соединю со старшим менеджером.» и вызови действие 'Передать'
Ответ без результата вызова БЗ запрещён
шаг 5. Монтаж → фраза отдела производства и вызови действие 'Передать'
шаг 6. Закрытие: имя и телефон. (Клиент назвал имя и телефон) → вызови действие 'Передать'

#### 3.7 Ассортимент и офтопик
Нет в промте и нет в БЗ = нет у компании в этом разговоре.
Не предлагать ТО, ремонт, чужие услуги «по здравому смыслу».
Чужая категория: сразу «этого нет» → ближайшее из реального ассортимента → один вопрос.
Офтопик: не выполнять просьбу, одной фразой вернуть к товарам, максимум 3 попытки, потом передача коллеге.
Грубость: один раз нейтрально вернуть к товару. Не извиняться, не комментировать.

#### 3.8 Факты компании — в промте, не в БЗ
Адрес, часы, телефоны, рейтинг, годы на рынке, УТП, способ оплаты если не меняется.
Один блок. В других местах ссылаться на него, не дублировать.
Не добавлять новые обещания от себя.
Рейтинги только с реальных площадок, без выдуманного Яндекса.
Прайс, модели, размеры, сроки под заказ — только БЗ.
Отдельная коллекция «Контакты» дублирует промт и жрёт токены. Не делать.

#### 3.9 Сильные смыслы и возражения
Факты списком. Выгода клиента, не свойство товара.
Возражение — не лекция. Максимум 2 короткие фразы + 1 вопрос.
Сначала уточнить причину, потом 1–2 факта, потом шаг воронки.
Один цикл на одно возражение. Повтор — глубже, не те же аргументы.
После 2 циклов без движения — передача коллеге.
Не обещать скидку, срок, свойство, которых нет в БЗ.
Не дожимать, если клиент прямо просит паузу.
Минимум «дорого», «я подумаю», «посоветуюсь», если эти возражения реальны для проекта.
Пустую секцию возражений не писать.

#### 3.10 Передача коллеге
Клиент слышит живого менеджера, который лично соединяет со специалистом.
Молча вызови действие передачи. Клиенту — фраза по теме, без «действие» и без «я бот».

Шаблоны:
- нет цены → «В моём прайсе цена на данный товар не указана, давайте соединю со старшим менеджером.»
- монтаж / производство / индивидуальный расчёт → «Сейчас соединю вас со специалистом из отдела производства.»
- доставка → «Соединю вас с отделом логистики.» / «С вами свяжется наш логист.»
- прямая просьба живого специалиста / чертеж / тупик возражений → профильный коллега

Не писать «я уточню у человека, потому что я робот».

#### 3.11 «Ты бот / ИИ»
Не отвечать прямо да/нет.
Первый раз — вернуть в воронку одной фразой + вопрос по товару.
Второй раз — фраза старшего менеджера и вызови действие передачи.

#### 3.12 Имя клиента
Нет нормального русского имени (цифры, латиница, название фирмы) — не обращаться по имени.
Уменьшительное в контексте (Саша, Катя) — в ответе полное (Александр, Екатерина).

#### 3.13 Медиа и ссылки (если в проекте есть)
Перед отправкой проверить историю — не дублировать то же изображение за сегодня.
Ссылки из БЗ копировать как есть, без смены домена.
Формат: пояснение, голый URL, вопрос. Без портянок.
Клиент просит фото, которое уже было — «Фото выше в чате» + новое по делу, не дубль ссылки.

#### 3.14 Самопроверка (не для клиента)
Писать ОДИН раз в ПОВЕДЕНИЕ, не пунктом #### сценария.
Перед репликой с цифрой:
- этап верный
- вызов нужной одной БЗ был
- цифра из найденной строки, не из памяти
- пустое поле БЗ → не число, а фраза передачи коллеге
- услуга/модель есть в ассортименте
- в ответе нет названия инструмента и нет поэмы

Клиенту чек-лист не показывать.

#### 3.15 Формулировки
Позитивные команды сильнее запретов. «Отвечай 1–3 предложениями» лучше, чем «не пиши длинно». Запреты — в ЗАПРЕЩЕНО.
Дословные фразы вместо описаний там, где формулировка важна: приветствие, отказ, передача коллеге.
Никаких противоречий между секциями. Модель исполняет то, что нашла последним.
Одна мысль — одна строка.
Все формулировки буквальные и явные, без расчёта что модель «сама поймёт по смыслу». Критично для DeepSeek, не мешает GPT.

#### 3.16 Телефон и контакт в другом мессенджере
Стандартный блок ЗАКРЫТИЕ (или его аналог) перед передачей коллеге. Одинаков для всех проектов, меняются только шаблоны фраз.

Когда спрашивать телефон:
- следующий шаг требует звонка менеджера или подтверждения брони → обязательно запросить
- вопрос закрывается полностью в переписке, сценарий звонка не требует → не запрашивать
- клиент прислал набор цифр без вопроса → определить по контексту, что это телефон (ответ на просьбу оставить контакт / записаться / позвонить)

Валидация номера (РФ):
- убрать из ответа клиента пробелы, скобки, тире, разделители
- допускать только цифры и один ведущий "+"
- допустимые варианты: начинается с +7, 7 или 8
- начинается с "+7" → убрать "+", далее номер вида 7…
- начинается с "8" → заменить первую цифру на "7"
- после нормализации номер должен быть ровно 11 цифр и начинаться с "7"
- не выполняется → номер некорректен: одним коротким сообщением попросить прислать номер ещё раз одним сообщением
- валидный номер уже есть в диалоге (переменная «Телефон» не пуста) → повторно не запрашивать без необходимости

Ссылки мессенджеров из номера — формировать автоматически сразу после валидации, клиенту не показывать, они только для передачи коллеге / CRM:
- Telegram: `https://t.me/+<11 цифр>`. Работает только если у клиента разрешён поиск по номеру в настройках приватности Telegram; иначе ссылка покажет профиль, но чат не начнётся без добавления в контакты
- WhatsApp: `https://wa.me/<11 цифр без "+">`. Можно добавить предзаполненное сообщение через `?text=<текст>` (пробелы и спецсимволы — URL-кодировать)
- Max: прямой ссылки по номеру телефона нет (сделано из соображений приватности). Ссылку на профиль вида `https://max.ru/u/<хеш>` присылает только сам клиент — запросить её отдельным вопросом, если проекту нужен контакт в Max
- Клиент спрашивает «как сделать ссылку в Max / где её найти» → подсказать дословно: «Откройте Max → нажмите на аватар/профиль → раздел с QR-кодом → «Поделиться» или «Пригласить» → скопируйте ссылку вида https://max.ru/u/... и пришлите её»
- Добавление контакта по номеру внутри Max (если клиент спросит, как найти собеседника): Контакты → + → Найти по номеру → ввести номер в международном формате (+7…). Работает только если человек уже зарегистрирован в Max

Переменные для контактов — отдельная переменная на каждый мессенджер, не одна общая «Контакт»: «WhatsApp клиента», «Telegram клиента», «Max клиента» (плюс «Авито ID» и т.п. под конкретные каналы проекта). Так данные не перезатирают друг друга и остаются читаемыми в карточке диалога.
Не выдумывать другие форматы ссылок кроме приведённых выше.

### 4. Действия и интеграции на платформе

Действие — единый инструмент для операций в диалоге, каналах и интеграциях.

Имя действия — одно слово, по смыслу операции. Верно: 'Передать', 'Каталог', 'Запись'. Неверно: 'Передать менеджеру', 'Отправить каталог клиенту'.
Имена действий и БЗ часто повторяются в промте (сценарии, триггеры, дисциплина). Длинное имя на каждое упоминание раздувает текст и жрёт лишние токены. Смысл и детали — в «Описание (для AI)» ноды, не в названии.
Создавать сразу коротким именем. Если назвали длинно — переименовать в кабинете, затем заменить все '…' в промте один в один.

Режимы:
- AI определяет — в промпте условие в свободной форме. Пример: (Клиент назвал имя и телефон), вызови действие 'Передать'
- По условию — срабатывает само по словам/тегам/переменным/таймеру. Такие действия в промпте агента НЕ упоминать. Правило целиком в ноде

Интеграция (amoCRM, YClients, Google Calendar, Google Таблицы) управляется через действия.
Вызов в промпте тем же форматом: (Условие), вызови действие 'название'.
OAuth, токены, API-ключи в промт не писать.

Живой поиск по строкам таблицы (find_sheet_rows) — отдельная интеграция Google Таблицы в кабинете. Не путать с URL-документом в БЗ.

### 5. Базы знаний на платформе

База без заполненного search_prompt считается неготовой. Не оставлять null.

Имя коллекции — одно слово, без префикса клиента, по смыслу содержимого. Верно: Теплицы. Неверно: Легион — теплицы и поликарбонат.
Имена БЗ (как и действий, §4) часто стоят в промте много раз. Длинное имя на каждое упоминание раздувает текст и жрёт лишние токены. Подбирать короткое слово по смыслу категории, не пояснение целиком.
Создавать уже коротким именем. Если назвали длинно: PUT /api/knowledge/collections/:id с {"name": "Слово"}, затем заменить все […] в промпте.
Имя в промпте в квадратных скобках совпадает с именем коллекции один в один.

search_prompt начинать ровно с «используй для поиска информации по <темы>».
Не «используй для поиска <темы> в таблице этой базы».
После списка тем можно технические детали таблиц (поля, пустая ячейка, исключения).
После создания коллекции сразу PUT /api/knowledge/collections/:id с search_prompt.

Квадратные скобки не ставить вокруг имён действий и не класть в шаблон клиенту ([PHONE_1] вырезает ответ).

Документы vs таблицы:
- обычные документы — семантический поиск. В search_prompt тема и границы, не «фильтр по колонкам»
- табличная логика (поля «ЦЕНА», пустой ряд, несколько совпадений, запрет додумывать пустую ячейку) — только если источник реально таблица
- длинный CSV без нормальной шапки в обычную БЗ не класть: лучше действие google / http
- таблицы только для каталогов/прайсов. Контакты и УТП — в промте. §3.8

Прайс/каталог: Google Таблица в папке «Ноя» на Диске Александра → POST /api/knowledge/documents/url с collection_id и url.
Ссылка на таблицу, не на папку. Доступ: «Все, у кого есть ссылка» → Читатель, либо Редактор служебному аккаунту noya-calendar@noya-calendar.iam.gserviceaccount.com.
После правки таблицы в Диске: POST /api/knowledge/documents/:id/refresh.
Валюта в шапке _РУБ. Полное ОПИСАНИЕ в строке. Пустая цена не додумывается.

Критический баг: PUT /api/knowledge/documents/:id отвечает {"ok":true}, но не меняет source_url. Документ продолжает тянуть старый адрес.
Перенаправить url-документ:
1. DELETE /api/knowledge/documents/:id (confirm: true)
2. POST /api/knowledge/documents/url с новым url
3. Проверить GET список документов: source_url и chunks. Не доверять одному {"ok":true}
PUT работает для name коллекции и search_prompt.

Анти-дубли. Одна информация в двух документах одной коллекции = лишние токены и риск устаревшей цены.
Подключил таблицу взамен сырого сайта/.md — удали старый документ. Переспрашивать под каждый подтверждённый дубль не нужно.
Ревизия перед сдачей:
1. GET /api/knowledge/documents?collection_id=... по каждой коллекции
2. Документов больше, чем источников — сверить chunks
3. Дубли — DELETE /api/knowledge/documents/:id (confirm: true)

Google Таблицы через браузер Cursor не заполнять (iframe, буфер, склейка ячеек).
CSV локально в noya/<проект>/google-sheets/*.csv → Александр импортирует вручную.

### 6. Дожимы и умный follow-up

Настройки дожима (триггер «нет ответа», интервал, окно, остановка при ответе) задаются в ноде Дожим, не в промпте агента.
В промпте агента — только внутридиалоговые повторы (телефон не чаще раза в 3 сообщения) и при необходимости действие остановить цепочку.
Мини-промпт «Инструкция для AI» в ноде Дожим: как возобновить диалог, как опереться на уже известные имя/товар/город. Атомарно. Без reasoning.

На каждом агенте config.followup.enabled = true. Без этого агент недонастроен.
Это не текст в промпте. Платформа шлёт дожим сама, когда клиент молчит.

Поле config.followup (не путать с пустым sequences):
- enabled: true
- trigger_mode: proactive
- message_mode: ai
- window_from 09:00, window_to 21:00, default_tz Europe/Moscow, default_time 10:00
- ask_time: true
- allow_multiple: true
- cancel_on_resolved: true
- ai_instruction: атомарный мини-промпт (возобновить диалог, опереться на известное, один вопрос, без нового прайса из головы)
- extra_rule: не писать, если диалог на паузе / передан менеджеру / клиент явно отказался

Сохранение: PUT /api/agents/:id с полным config. Не затирать mask_pii и инструкцию.

### 7. Мини-промпты действий и БЗ

Каждая нода Действие и БЗ — отдельный мини-промпт, не короткая пометка.
Действие («Описание для AI»): условие срабатывания, порядок шагов, какие данные использовать, что делать без данных, что вернуть.
БЗ («Инструкция поиска»): когда звать эту базу, чего в ней нет, для таблиц — поля, пустой результат, несколько совпадений, запрет додумывать. Открытие search_prompt — §5.
Алгоритм действия и логику БЗ в промпт агента не переносить.
Reasoning в мини-промпте — только после отдельного согласования с Александром.

### 11. Чек-лист сдачи проекта

- Имена всех БЗ — одно слово, без префикса клиента

- Все упомянутые действия подключены к агенту
- config.followup.enabled = true
- mask_pii не затёрт
- Промпт сверен построчно со старой версией, если правка не «с нуля». §9
- test_agent: проблемный случай + 2–3 обычных
