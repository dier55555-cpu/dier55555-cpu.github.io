# Парсинг сайтов судов (ГАС «Правосудие») → база знаний ИИ-агента в НОЕ

Каркас для сбора информации с сайтов районных судов (шаблон sudrf.ru) и
подготовки её к использованию агентом: либо как документы в Базе Знаний (БЗ)
платформы, либо как «живой» MCP-инструмент.

Суды из задачи (см. `courts.yaml`):

- Советский районный суд г. Воронежа
- Коминтерновский районный суд г. Воронежа
- Железнодорожный районный суд г. Воронежа
- Левобережный районный суд г. Воронежа
- Центральный районный суд г. Воронежа
- Ленинский районный суд г. Воронежа

## Главное ограничение: сайты блокируют иностранные IP

Проверено вручную прямо из этого окружения (см. `data/summary.json` после
запуска) — **все 6 сайтов возвращают HTTP 200, но с телом-заглушкой**:

```
Судебный департамент при Верховном Суде Российской Федерации
Этот запрос заблокирован по соображениям безопасности (G)
Ваш ip: 3.136.249.249 ... United States, Columbus
```

Это WAF-блокировка по геолокации/типу IP (не-российские и/или дата-центровые
адреса), а не что-то специфичное для этого агента — та же проблема описана
у независимых разработчиков парсеров ГАС «Правосудие» (например,
[tochno-st/sudrfscraper](https://github.com/tochno-st/sudrfscraper)) и в
статьях про сбор судебных данных. Официального открытого API у ГАС
«Правосудие» нет.

**Вывод: этот скрипт нужно запускать с сервера или через прокси с российским
IP.** Из облака/зарубежного хостинга без RU-прокси данные не получить —
в `--proxy` передайте российский HTTP(S)-прокси или разверните скрипт на
VPS в РФ (Timeweb, Selectel, Beget и т.п.).

Часть судов (в тесте — Центральный) вместо HTML-страницы блокировки просто
рвёт TCP-соединение (`Connection reset by peer`) — скрипт распознаёт и это
как признак блокировки (см. `scraper/fetch.py`).

## Архитектура: два слоя данных

Вопросы клиентов к судебному ИИ-агенту делятся на два типа, и решать их
одним и тем же способом невыгодно:

### Слой 1 — статический справочник (закрывает большинство вопросов)

Адрес, контакты, режим работы приёмной, реквизиты для оплаты госпошлины/
штрафов, судебные участки и составы, порядок подачи документов, часто
задаваемые вопросы, новости. Меняется редко.

**Как отдать агенту:** гонять `scraper/crawl.py` по расписанию (например,
раз в сутки или раз в неделю через cron), складывать текст в
`data/<court_slug>/pages.jsonl` и `data/corpus.jsonl`, дальше **загружать эти
тексты как документы в Базу Знаний агента в НОЕ** (через встроенный импорт
документов/URL платформы, либо через её API загрузки в БЗ, если он есть).
Обновлять в БЗ нужно только то, что реально изменилось — для этого в каждой
записи есть `text_hash`, сравнивайте его с предыдущим прогоном.

### Слой 2 — динамика (поиск дела по номеру/ФИО, статус, движение дела)

Реализован в `scraper/case_lookup/` + MCP-инструмент `court_case_lookup`
(см. раздел «Слой 2 подробно» ниже). Это НЕ предзагружается в БЗ разово —
данные специфичны под конкретного пользователя (номер дела/участник) и
могут поменяться в любой момент, поэтому инструмент делает живой запрос к
сайту суда в момент вопроса пользователя, а не отвечает по кэшу.

## Структура проекта

```
court-kb/
  courts.yaml           # список судов (slug, название, base_url, case_search)
  scraper/
    fetch.py             # HTTP-слой: ретраи, паузы, детект блокировки, robots.txt
    extract.py           # извлечение ссылок и основного текста (trafilatura)
    crawl.py             # обход сайта суда, запись pages.jsonl/report.json (слой 1)
    case_lookup/
      forms.py            # эвристический разбор формы поиска дела (sud_delo)
      case_card.py         # разбор карточки дела / результатов поиска
      captcha.py           # решатели капчи (2captcha, ручной ввод)
      search.py            # оркестрация: форма -> капча -> отправка -> результат
      discover.py           # CLI-разведка формы конкретного суда (см. ниже)
  mcp_server/
    server.py             # MCP-сервер: court_kb_search, court_kb_list_courts, court_case_lookup
  tests/                   # юнит-тесты на синтетических HTML-фикстурах
  data/                   # результат обхода (в git не коммитится)
```

## Запуск сбора данных

```bash
pip install -r requirements.txt

# с российского IP/прокси:
python -m scraper.crawl --config courts.yaml --out data \
    --max-pages 60 --max-depth 2 \
    --proxy http://user:pass@ru-proxy-host:port

# точечно по одному суду:
python -m scraper.crawl --config courts.yaml --out data --only sovetsky-vrn
```

После запуска смотрите `data/summary.json` — там по каждому суду видно,
сколько страниц собрано и не заблокирован ли сайт.

Скрипт уважает `robots.txt`, ходит с задержкой 2–5 сек между запросами
(настраивается `--min-delay/--max-delay`) и не забирает файлы (pdf/doc/картинки).
**Не увеличивайте частоту запросов** — это гос. сайт, агрессивный обход может
привести к дополнительным блокировкам или расцениваться как нагрузочная
атака.

### Автоматизация (пример cron, раз в сутки ночью)

```cron
0 3 * * * cd /path/to/court-kb && /path/to/venv/bin/python -m scraper.crawl \
    --config courts.yaml --out data --proxy "$RU_PROXY_URL" >> cron.log 2>&1
```

После обновления `data/` — прогоняете скрипт синхронизации с БЗ платформы
(его нужно написать под конкретное API НОЕ; общий принцип: сравнить
`text_hash` с предыдущей выгрузкой, залить только изменённые/новые страницы).

## Запуск MCP-сервера (слой 1 + слой 2)

```bash
export COURT_KB_PROXY="http://user:pass@ru-proxy-host:port"   # обязателен для слоя 2 (и полезен для слоя 1)
export TWOCAPTCHA_API_KEY="..."                                 # если на форме суда есть капча

python -m mcp_server.server --corpus data/corpus.jsonl --courts-config courts.yaml
```

Поднимает stdio MCP-сервер с инструментами:

- `court_kb_search(query, court_slug=None, top_k=3)` — слой 1: поиск
  релевантных фрагментов по заранее собранной базе.
- `court_kb_list_courts()` — список судов в базе.
- `court_case_lookup(court_slug, case_number=None, last_name=None,
  production_type="civil_first_instance")` — слой 2: живой поиск дела на
  сайте суда (требует `case_search.enabled: true` в `courts.yaml` для этого
  суда — включайте только после `discover.py`, см. выше).

Подключается в НОЕ как обычный внешний MCP-сервер (stdio-транспорт). Поиск
в `court_kb_search` сейчас простой, по совпадению слов — для продакшена
замените `score()` в `mcp_server/server.py` на векторный поиск (embeddings
+ FAISS/pgvector), интерфейс инструмента для агента не изменится.

## Слой 2 подробно: поиск дела по номеру/ФИО

Реализация — `scraper/case_lookup/`. Идея: не парсить весь массив дел
заранее (это и не нужно, и рискованно с точки зрения нагрузки/персональных
данных), а по каждому вопросу пользователя ("когда у меня заседание по делу
№…", "есть ли дела с моей фамилией") делать один живой запрос через форму
«Судебное делопроизводство» (`modules.php?name=sud_delo`) и сразу отдавать
ответ агенту.

### Как это устроено технически

1. `forms.py` загружает страницу формы поиска и **эвристически** сопоставляет
   подписи полей ("Фамилия", "Номер дела (материала)", "Уникальный
   идентификатор дела", "Проверочный код") с их реальными HTML `name`-
   атрибутами — жёстко их не зашиваем, т.к. они отличаются от сборки к сборке
   (это подтверждается и другими независимыми парсерами ГАС «Правосудие»).
2. Если на форме есть капча — `captcha.py` скачивает картинку и отдаёт её
   решателю (`TwoCaptchaSolver` — платный сервис 2captcha/rucaptcha, либо
   `ManualCaptchaSolver` — ручной ввод в консоли для тестового прогона).
3. `search.py` заполняет форму, отправляет её (GET или POST — как указано в
   `<form method=...>`), при неверной капче повторяет попытку (до
   `max_captcha_attempts`), и передаёт HTML результата в `case_card.py`.
4. `case_card.py` разбирает секции карточки дела (ДАННЫЕ ПО ДЕЛУ, ДВИЖЕНИЕ
   ДЕЛА, СТОРОНЫ ПО ДЕЛУ и т.п.) — тоже эвристически, по признаку "строка
   таблицы из одной непустой ячейки текстом в ВЕРХНЕМ РЕГИСТРЕ = заголовок
   секции", без привязки к конкретным названиям (они у судов отличаются).
5. `mcp_server/server.py` регистрирует инструмент `court_case_lookup(court_slug,
   case_number, last_name, production_type)`, который агент в НОЕ вызывает
   прямо во время диалога с пользователем.

Всё покрыто юнит-тестами (`tests/test_forms.py`, `tests/test_case_card.py`,
`tests/test_search.py`) на синтетических HTML-фикстурах, воспроизводящих
реальную структуру формы/карточки (подтверждённую на других сайтах ГАС
«Правосудие» — СПб, Башкортостан — через открытые источники, т.к. с сайтами
самих 6 судов Воронежа прямое сравнение верстки недоступно из-за геоблока).

### Что нужно сделать перед включением на бою (обязательно, руками, с RU IP)

Автоматическое сопоставление полей — лучшее, что можно сделать без доступа
к реальной странице, но его нужно подтвердить:

```bash
python -m scraper.case_lookup.discover \
    --config courts.yaml --slug sovetsky-vrn --delo-id 1540005 \
    --proxy http://user:pass@ru-proxy-host:port
```

Команда сохранит найденные поля формы и наличие капчи в
`data/sovetsky-vrn/case_search_form_1540005.json`. Дальше:

- Если в выводе `unmapped_visible_fields` пусто — эвристика справилась,
  можно включать `case_search.enabled: true` в `courts.yaml` для этого суда.
- Если что-то не сопоставилось — допишите `case_search.field_overrides`
  (`case_number`/`case_uid`/`last_name` -> реальное имя поля из отчёта).
- Если `captcha` не `null` — настройте `TWOCAPTCHA_API_KEY` (переменная
  окружения для MCP-сервера) либо используйте `COURT_KB_MANUAL_CAPTCHA=1`
  только для ручного тестирования (не для продакшен-ответов агента).
- Значения `delo_id` (1540005 — гражданские первой инстанции, 1540006 —
  уголовные первой инстанции) подтверждены на других сайтах ГАС «Правосудие»
  и, по всей видимости, одинаковы для всей платформы — но обязательно
  прогоните `discover.py` и для этих 6 судов, прежде чем доверять им.

Прогоните `discover.py` для каждого суда и каждого нужного `production_type`
(гражданские/уголовные/административные — под административные и
материалы `delo_id` пока не подтверждён вообще, ищите его тем же способом:
переберите значения из открытых примеров или найдите ссылку на форму этого
типа в меню самого сайта суда).

### Ограничения по использованию (важно)

- Этот инструмент рассчитан на **одиночные запросы по конкретному делу/
  фамилии от конкретного пользователя**, а не на массовый обход всех дел
  суда — для мониторинга всех исков к клиенту (другая, более
  чувствительная задача) нужен отдельный, гораздо более аккуратный по
  нагрузке и юридическим рискам процесс.
- Решение капчи стоит денег и занимает время (несколько секунд) — не
  вызывайте `court_case_lookup` "на всякий случай", только когда пользователь
  явно спросил про конкретное дело.
- Результат не кэшируется намеренно (данные о деле должны быть свежими),
  но при необходимости добавьте короткий TTL-кэш (1–5 минут) в
  `mcp_server/server.py`, чтобы повторные уточняющие вопросы одного
  диалога не дёргали капчу заново.

### Рендеринг JS-версий отдельных судов (вне MVP)

У некоторых судов результаты поиска подгружаются через JavaScript (в
статье на Хабре упоминается Советский районный суд г. Казани — не путать с
Советским районным судом г. Воронежа из этой задачи, но подобное можно
встретить и здесь). `requests`-based `search.py` такое не увидит — если
`discover.py` вернёт пустую/нерелевантную форму, следующим шагом будет
переписать `forms.py`/`search.py` на Playwright (headless-браузер) вместо
`requests`.

## Запуск тестов

```bash
python -m pytest tests/ -v
```

Тесты не ходят в сеть — они проверяют логику разбора формы/капчи/карточки
дела на синтетических HTML-фикстурах, воспроизводящих реальную структуру.

## Юридические и этические моменты

- ФЗ №262 «Об обеспечении доступа к информации о деятельности судов»
  формально гарантирует открытость этой информации (в т.ч. сведений о
  конкретных делах — ст. 4, 8), но сами сайты технически защищаются
  (геоблок, где-то — JS/капча). Автоматизированный обход не запрещён
  напрямую, но соблюдайте `robots.txt`, не создавайте нагрузку (задержки
  между запросами, не парсите параллельно все 6 сайтов одним потоком) и
  укажите контакт в `User-Agent` (см. `DEFAULT_USER_AGENT` в
  `scraper/fetch.py`).
- **Слой 2 (поиск дела) реализован и возвращает персональные данные**
  участников (ФИО истцов/ответчиков, судей, иногда ИНН/ОГРН). Так как агент
  пересказывает их пользователю, учитывайте 152-ФЗ «О персональных
  данных»: отвечайте только на конкретный запрос конкретного пользователя о
  конкретном деле (по номеру или фамилии, которую он сам назвал), не
  сохраняйте результаты дольше, чем нужно для ответа в текущем диалоге, и
  не используйте `court_case_lookup` для массового перебора фамилий/номеров.
- Суды обязаны обезличивать чувствительные данные на своих страницах
  (даты/суммы по делам о компенсации морального вреда, персональные данные
  в некоторых категориях дел скрываются самим судом) — то, что вернул
  `court_case_lookup`, это то же самое, что видит любой посетитель сайта в
  браузере, никаких дополнительных данных агент не получает.
