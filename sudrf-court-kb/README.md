# sudrf-court-kb

Инструмент, который собирает публичную информацию с сайтов районных судов
Воронежа (домены `*.sudrf.ru`) и превращает её в базу знаний для ИИ-агента —
либо в виде готовых markdown/JSON-файлов для загрузки в «БЗ» вашей платформы
(например, НОЯ), либо в виде живого MCP-сервера, который агент может вызывать
во время диалога.

Этот каталог — самостоятельный проект, не связанный с остальным содержимым
репозитория (которое обслуживает статическую страницу политики
конфиденциальности другого продукта). Разместите его в отдельном репозитории /
на своём сервере, когда будете разворачивать в проде — здесь он лежит как
готовый, рабочий прототип.

## Почему это НЕ обычный парсер «запустил у себя — и работает»

Сайты `*.sudrf.ru` (ГАС РФ «Правосудие») **блокируют весь трафик не из
российских IP-адресов** на уровне инфраструктуры (WAF отвечает `HTTP 200/403`
со страницей «Этот запрос заблокирован по соображениям безопасности (G)»).
Это подтверждено вживую с этой машины (US IP) для всех 6 сайтов из вашего
списка. Значит:

- Запускать краулер нужно **с сервера с российским IP** (VPS в Selectel,
  Yandex Cloud, VK Cloud, Timeweb и т.п.) либо через российский прокси.
- Запускать его **из Cursor Cloud Agent или любого зарубежного CI/CD —
  бессмысленно**, запросы будут блокироваться на уровне сети.
- CAPTCHA/защита от автоматизации на самих сайтах не проверялась (не было
  доступа), поэтому код написан максимально «вежливо» (задержки между
  запросами, честный User-Agent, соблюдение robots.txt) и универсально
  (не завязан на конкретную разметку HTML, а обходит ссылки внутри домена и
  вытаскивает основной текст страницы). После первого запуска с российского
  IP почти наверняка понадобится точечная донастройка селекторов под
  реальную разметку — см. `sudrf_kb/parse.py`.

## Архитектура: два способа отдать данные агенту

### 1. Статическая база знаний (БЗ) — для большинства случаев

Реквизиты, адреса, график приёма, состав суда, новости, порядок подачи
документов — это медленно меняющийся справочный контент. Его не нужно
дёргать «вживую» на каждый вопрос клиента: достаточно раз в день/неделю
прогнать краулер, собрать чистый markdown/JSON на каждый суд и загрузить
получившиеся файлы в «БЗ» агента в НОЯ (как обычные документы знаний).
Это самый простой, дёшёвый и надёжный вариант — никакого постоянно работающего
сервера агенту не нужно, только cron-задача на VPS + выгрузка файлов туда,
куда их принимает платформа (загрузка документов в БЗ / вебхук / API, если
у НОЯ есть API загрузки знаний).

### 2. MCP-инструмент — для «живых» данных

Если агенту нужно отвечать на вопросы вида «а что с моим делом
№2-1234/2025» или «когда следующее заседание по делу», статическая БЗ не
подходит — эти данные надёжно нельзя закешировать заранее. Для этого в
`sudrf_kb/mcp_server.py` реализован MCP-сервер с инструментами, которые
агент вызывает во время диалога. Такой сервер тоже должен работать на
российском IP (см. выше) и быть постоянно доступным (не батч-задачей, а
процессом/сервисом).

**Важное юридическое замечание:** карточки судебных дел могут содержать
персональные данные третьих лиц (ФИО сторон, судей и т.п.). Если планируете
автоматически подтягивать данные по конкретным делам в ответ агента клиенту —
убедитесь, что это соответствует 152-ФЗ «О персональных данных» и правилам
самой ГАС «Правосудие» (проверьте `robots.txt` и условия использования каждого
сайта). Для MVP рекомендуется ограничиться агрегированной публичной
информацией (раздел 1) и не автоматизировать поиск по ФИО/номерам дел без
отдельной юридической проверки.

## Что уже сделано

- `config/courts.yaml` — конфигурация 6 судов Воронежа из вашего списка.
- `sudrf_kb/fetch.py` — вежливый HTTP-клиент: rate-limit, ретраи,
  уважение `robots.txt`, понятный User-Agent.
- `sudrf_kb/crawler.py` — обход сайта в пределах домена (BFS, ограничение
  глубины/количества страниц), пропуск бинарников/служебных ссылок.
- `sudrf_kb/parse.py` — очистка HTML и извлечение «полезного» текста
  страницы (заголовок + основной контент, без меню/футера/скриптов) плюс
  простая классификация страницы по типу (новости/контакты/структура/
  реквизиты/прочее) по ключевым словам — при необходимости замените на
  точные CSS-селекторы конкретного суда.
- `sudrf_kb/kb_builder.py` — собирает результаты обхода в:
  - `data/<court_id>.json` — структурированные данные по суду;
  - `data/<court_id>.md` — то же самое в markdown, готовое к загрузке в БЗ;
  - `data/all_courts.md` — общий файл по всем 6 судам.
- `sudrf_kb/mcp_server.py` — MCP-сервер (`FastMCP`) с инструментами:
  - `list_courts` — список судов и их ID;
  - `get_court_info(court_id)` — контакты/реквизиты/график/структура суда;
  - `search_courts(query)` — полнотекстовый поиск по собранной базе знаний
    (по всем судам сразу или по одному);
  - `refresh_court(court_id)` — принудительно перекраулить один сайт
    (используйте с осторожностью — это живой сетевой запрос).
- `sudrf_kb/cli.py` — командная строка: `crawl`, `build-kb`, `serve-mcp`.

## Быстрый старт (на российском VPS)

```bash
cd sudrf-court-kb
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 1. Обойти все сайты и сохранить сырые страницы + разбор
python -m sudrf_kb.cli crawl --all

# 2. Собрать базу знаний (markdown/JSON) из результатов обхода
python -m sudrf_kb.cli build-kb

# файлы появятся в sudrf-court-kb/data/*.md и *.json —
# их можно грузить в «БЗ» агента в НОЯ

# 3. (опционально) поднять MCP-сервер для live-инструментов
python -m sudrf_kb.cli serve-mcp --transport stdio
# либо через SSE/HTTP для удалённого подключения из НОЯ:
python -m sudrf_kb.cli serve-mcp --transport sse --host 0.0.0.0 --port 8765
```

## Регулярное обновление (cron)

Пример: обновлять базу знаний каждый день в 03:00 по MSK и логировать
результат:

```cron
0 3 * * * cd /opt/sudrf-court-kb && .venv/bin/python -m sudrf_kb.cli crawl --all && .venv/bin/python -m sudrf_kb.cli build-kb >> /var/log/sudrf-kb.log 2>&1
```

После обновления файлов `data/*.md` останется только повторно загрузить их
в «БЗ» доски агента в НОЯ (руками через интерфейс либо через API/вебхук,
если платформа его предоставляет — сообщите точку загрузки, и в
`sudrf_kb/kb_builder.py` можно добавить автоматическую отправку туда).

## Как подключить MCP-сервер к НОЯ

Если платформа НОЯ поддерживает подключение внешних MCP-серверов (как в
первой части вашего вопроса про Легион), укажите там адрес запущенного
`serve-mcp --transport sse` процесса (например,
`https://your-ru-vps.example.com:8765/sse`, желательно за reverse-proxy с
TLS и токеном авторизации — добавьте basic-auth/API-key на уровне nginx,
сам MCP-протокол авторизации не содержит). Тогда агент сможет вызывать
`get_court_info` / `search_courts` прямо в диалоге, без ожидания ночного
обновления БЗ.

## Дальнейшие шаги, которые стоит сделать вам на месте (с RU IP)

1. Запустить `crawl --all` с российского сервера и посмотреть на реальные
   `data/raw/*.html` — проверить, не потребовалась ли капча/JS-рендер
   (если да — добавить Selenium/Playwright, в коде оставлен точка
   расширения `fetch.py::fetch_page`).
2. Уточнить селекторы в `parse.py` под реальную разметку (сейчас это
   эвристика: убираем `nav/header/footer/script/style`, дальше берём
   заголовок + основной блок текста — этого достаточно для контактов/новостей,
   но для табличных данных вроде графика приёма может понадобиться
   отдельный парсер таблиц).
3. Решить, куда именно грузить готовые `data/*.md` в НОЯ (ручная загрузка,
   API, вебхук) и, если есть API, дописать `kb_builder.py::publish_to_noya`.
