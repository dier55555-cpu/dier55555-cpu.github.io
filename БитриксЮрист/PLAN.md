# БитриксЮрист

Третий контур: план из `court-monitor` + ваш `bitrix.py` + парсер Анны на VPS.  
**Анну, её промпт, БЗ, MCP и воркфлоу `court-agent-yurist` не трогаем.**

---

## Ответы сразу

**Писать в чат карточки сделки — да.**  
В Битрикс это таймлайн сделки: метод `crm.timeline.comment.add`, `ENTITY_TYPE=deal`, `ENTITY_ID=<id сделки>`. В комментарии ставим факт:

```
[БитриксЮрист] Обновление дела произведено
Проверено: 22.08.2026 06:14 (МСК)
Номер: 2-1248/2026
Статус на сайте: …
Следующее заседание: …
Что изменилось: …
Карточка суда: https://…
```

Дата/время берём с сервера в `Europe/Moscow` в момент успешной проверки, не «примерно утром». Клиент или юрист, открыв карточку, видит запись в ленте.

Важная оговорка: лента карточки — это **CRM**. Её видят сотрудники портала. Внешний клиент в WhatsApp/Telegram эту строку сам не получит, пока отдельно не подключим открытую линию или SMS. В MVP «клиент понимает по факту» = запись в карточке сделки. Сообщение в мессенджер — этап 2, не через Анну.

**n8n / Ноя для этого проекта не нужны.**  
Будильник, Битрикс REST и вызов парсера собираем **на том же VPS**, где уже крутится Аннин `/delo` (`systemd timer` в 06:00 МСК). Ноя остаётся только для чата Анны. Её воркфлоу `court-agent-yurist` не трогаем и **новый n8n не заводим** — иначе снова таймаут шлюза ~30 с и лишняя точка отказа.

**Настройки парсера Анны — да, переиспользуем как чёрный ящик.**  
Анна ходит: её n8n → `POST http://127.0.0.1:8080/delo` (снаружи был `77.222.55.230:8080`) + `X-API-Key` → Python → sudrf через пул `proxy.market:10001–10010`.  
БитриксЮрист на том же сервере бьёт в `http://127.0.0.1:8080/delo`. `delo_app.py` и JSON Анны не копируем и не правим.

```json
{
  "mode": "case",
  "court_slug": "sovetsky-vrn",
  "case_number": "2-1248/2026",
  "last_name": null,
  "production_type": "civil_first_instance"
}
```

Ответ тот же `{status, result}`. Живая карточка на пилоте — только 6 райсудов Воронежа (как у Анны).

## Архитектура (всё на VPS парсера)

```
Один сервер (где уже /opt/court-kb и unit court-kb-delo :8080)

  systemd timer  БитриксЮрист  06:00 Europe/Moscow
        │  python -m bitrix   или  POST localhost:8081/run
        ▼
  Python «БитриксЮрист»   порт 8081, Аннин :8080 не занимаем
        │  1. crm.deal.list  — входящий вебхук Битрикс (не Ноя)
        │  2. для каждой сделки: POST http://127.0.0.1:8080/delo
        │  3. diff снимка
        │  4. crm.deal.update + crm.timeline.comment.add
        ▼
  Битрикс24 карточка (поля + лента)
```

Ноя в этой схеме не участвует. Парсер sudrf как был — Python + резидентный прокси.

## Чат карточки: как именно

Метод:

```http
POST {BITRIX_WEBHOOK_URL}/crm.timeline.comment.add.json
```

```json
{
  "fields": {
    "ENTITY_ID": 12345,
    "ENTITY_TYPE": "deal",
    "COMMENT": "[БитриксЮрист] Обновление дела произведено\nПроверено: 22.08.2026 06:14 (МСК)\n..."
  }
}
```

Правила:

- Пишем **после успешного** ответа парсера (`status=found`), с фактическим `datetime.now(MSK)`.
- Если на сайте **ничего не изменилось** — всё равно короткий комментарий раз в сутки *или* только поле «Проверено» без спама в ленту (решение на пилоте: по умолчанию комментарий **только при изменении**; поле даты проверки — **всегда**).
- Если дело не найдено / капча / WAF — комментарий менеджеру с пометкой «клиенту не слать», без формулировки «дело обновлено».
- Не дублировать тот же `content_hash` дважды за сутки.

## Пошаговый план работ

### Шаг 0. Не ломать Анну

- Не открывать и не сохранять `court-agent-yurist`.
- Не менять systemd `court-kb-delo`, пока не понадобится новый эндпоинт — MVP только читает `/delo`.
- Не менять промпт/агента «Анна».

### Шаг 1. Снять с портала (без этого код не живой)

- Входящий вебхук Битрикс, право CRM (таймлайн + сделки).
- `CATEGORY_ID`, рабочие `STAGE_ID`.
- Коды UF: номер дела, суд/slug/URL, статус с сайта, дата проверки, хеш снимка (или снимок только в файле сервиса).

### Шаг 2. Каркас этого каталога (сейчас)

- `bitrix.py` — третий вариант адаптера.
- `.env.example`, README, `deploy/*.service` + `*.timer`.
- Локальные снимки `data/snapshots.json`.
- Папка `n8n/` — черновик на всякий случай, **в прод не импортируем**.

### Шаг 3. Подключить тот же парсер

Python вызывает `POST {COURT_KB_API_URL}/delo` с `X-API-Key` как у Анны.  
Маппинг суда: поле сделки → один из slug:

`sovetsky-vrn`, `kominternovsky-vrn`, `zheleznodorozhny-vrn`, `levoberezhny-vrn`, `centralny-vrn`, `lensud-vrn`.

Нет slug — сделка в лог ошибок, `/delo` не дёргаем.

### Шаг 4. Расписание на том же VPS

Юнит `deploy/bitrix-yurist.timer`: `OnCalendar=*-*-* 06:00:00`, `WorkingDirectory` рядом с парсером.  
Ручной прогон: `systemctl start bitrix-yurist.service`.  
Порт `8081` нужен только если хотите HTTP `/run` / `/health`; для cron достаточно `python3 bitrix.py`. Аннин `:8080` не трогаем.

### Шаг 5. Пилот

`DRY_RUN=1` — только лог. Потом запись полей без комментария. Потом комментарий в тестовую сделку. Потом рабочие стадии.

### Шаг 6. Позже (не блокирует MVP)

Сообщение клиенту в открытую линию / SMS. Отдельный кусок, Анну не используем как автора текста.

## Риски, уже известные с Анны

- Датацентровый IP не открывает sudrf — только тот же residential пул (уже на этом VPS).
- `/delo` пилот — 6 судов Воронежа.
- Общий API: лишний дневной прогон не должен забить прокси так, чтобы днём Анна не могла ответить. Пауза 3–8 с между делами, старт в 06:00.

---

## Критерий готово

1. Воркфлоу Анны без изменений, живой поиск в чате как был.
2. В 06:00 systemd timer на VPS запускает БитриксЮрист. n8n Анны без изменений.
3. У тестовой сделки в ленте есть комментарий с датой и временем проверки.
4. При реальном изменении на сайте — новый комментарий «что изменилось»; без изменения — обновлена только дата проверки в поле.
